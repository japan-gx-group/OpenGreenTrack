# SSBJ 開示レポート R1 の試行手順（T15）

チームがローカル環境とデモデータで R1 を試すための、準備・手順・制限事項・反映と切り戻し・情報の区分をまとめる。
この文書は「R1 をどう試すか」を正とする。R1 で何を扱うかは [`ssbj-r1-scope.md`](ssbj-r1-scope.md)、
データ契約と保存の仕組みは [`ssbj-spec.md`](ssbj-spec.md) を正とし、ここでは繰り返さない。

> R1 は社内確認用の試行版であり、SSBJ 基準への準拠の認定・第三者保証・対外提出の完了を意味しない
> （[`ssbj-r1-scope.md`](ssbj-r1-scope.md) §1）。試行の結果を、準拠を確認した成果物として扱わない。

---

## 1. 試行の範囲

| 項目 | 内容 |
|---|---|
| 環境 | ローカル（Docker 上のローカル Supabase と、`ssbj` ブランチの開発サーバ） |
| データ | デモデータ（架空の組織・ユーザー・排出量）だけを使う。実在の企業のデータは入れない |
| 実施者 | チーム |
| 対象外 | 外部の環境への公開、実データでの試行 |

## 2. 準備

1. `ssbj` を最新にする（`git switch ssbj` → `git pull`）。依存が変わっていれば `npm ci`。
2. ローカル Supabase を起動し、マイグレーションを適用する（`npx supabase start` → `npx supabase migration up --local`）。
   初めて動かす場合の手順は [`setup-guide.md`](setup-guide.md) を参照。
3. デモデータを入れる（`npm run db:seed:demo`）。
   - `supabase/seeds/demo/` の `demo.sql`（デモ組織・ユーザー・排出量）と `ssbj_demo.sql`（入力例の入った SSBJ レポート）が流れる。
   - **デモ組織のデータは消してから入れ直す。** 手元でデモ組織に入力した内容は消える。DB 全体を作り直すときは
     `npm run db:reset:demo`（ローカルのすべてのデータが消える）。
4. 開発サーバを起動する（`npm run dev` → http://localhost:3000）。
5. **試行の前に全体テストを流し、すべて通ることを確かめる**（`npx playwright test -c playwright.ssbj.config.ts`。
   前提・確認している内容は [`ssbj-spec.md`](ssbj-spec.md) §13「R1 の全体テスト（T14）」）。通らなければ試行しない。

使うアカウント（デモデータの公開パスワード。`supabase/seeds/demo/demo.sql`）:

| アカウント | 組織 | 使いどころ |
|---|---|---|
| `org-a@example.com` / `password123` | 架空精密工業株式会社 | 試行の本体。2024 年度に OGT の算定値・Scope 3 の直接入力・サプライヤー別排出量と、入力例の入った SSBJ レポートがある |
| `org-b@example.com` / `password123` | 架空ロジスティクス株式会社 | 組織分離の確認（組織 A のレポートが見えないこと） |

## 3. 試行の手順

入力例の入ったレポート（「架空精密工業株式会社 サステナビリティ関連財務開示（試行）2024年度」）で画面を見て回るか、
新しくレポートを作って一通り入力する。新しく作る場合の手順と、各画面で確かめることを示す。

| # | 画面 | 操作 | 確かめること |
|---|---|---|---|
| 1 | SSBJレポート（`/ssbj`） | ヘッダーで「2024年度」を選び、「新規作成」でレポート名を入れて作成する | 一覧に出る。試行版である旨の注記が出ている |
| 2 | レポート詳細 | 基本情報の「編集」で、親会社名・親会社との関係・持分比率・測定アプローチ・業種を入れる | 業種に産業別ガイダンスの該当する巻へのリンクが出る |
| 3 | 四本柱の文章 | 項目ごとに「編集」で、開示する文章の状態と本文、内部メモを入れる。「テンプレートを入れる」で文例を入れ、【 】を書き換える | 各項目に要求 ID・項番号・記載ガイド・記載例が出る。【 】が残ったままでは入力済みにできない。本文を入れたまま状態を「未確認」にして保存すると、本文が保存されない旨の警告が出る。右側のプレビューに入力中の文章がその場で出る。「OGT の値」タブに最新の排出量が出る |
| 4 | リスク・機会 | 「リスク・機会を追加」で登録する。「時間軸の定義」を入れる | リスクだけに種類（物理的 / 移行）がある。説明と内部メモが分かれている |
| 5 | 該当性・重要性の判断 | 要求ごとに「編集」で、該当性・重要性・記載しない理由・開示する説明・内部の検討理由を入れる | 既定はすべて未確認。経過措置を選んで説明が空なら「その旨の説明が未入力」と出る |
| 6 | GHG排出量の候補値 | 候補値と算定条件を見て「表示中の候補値を採用する」 | 算定値の無い区分は 0 ではなく「未算定」。Scope 2 は基準不明で係数の種類ごとの内訳が付く。サプライヤー別は参考値として分かれている |
| 7 | 根拠文書・主管部署 | 「根拠文書を追加」で、項目・資料名・主管部署・開示用参照文を入れる | 資料名・保管先などは内部記録として、開示用参照文と分かれている |
| 8 | レポート詳細 | 「保存版を作成」。「状態と承認」で自分以外の承認者（例: `member-a@example.com` の算定 花子）を選んでレビューを依頼し、承認者のアカウントで承認する | 「版 1 として保存しました」と出る。承認者の選択肢に自分は出ない。依頼した本人には承認ボタンが押せない（理由が出る）。承認すると承認時の保存版ができ、各画面が編集できなくなる（承認者でない入力担当者には承認ボタンが押せない） |
| 9 | 保存履歴と出力 | 「内容を見る」「CSVを出力」「Excelを出力」「この版から新版を作成」。差戻した後で「この版の内容に戻す」 | CSV・Excel は保存版から作られ、版 ID・単位・位置付けが入る。復元すると、戻す前の内容が保存版として自動で残る |
| 10 | プレビュー | 「表示する内容」で作業中と保存版を切り替え、「内部メモも表示する」を切り替え、「印刷・PDFとして保存」 | 作業中か保存版かが先頭に出る。内部メモは選んだときだけ出る。未入力・未確認は状態の名前で出る |
| 11 | （元データの変更） | 保存版を作った後で文章を書き換え、プレビューで保存版を選ぶ | 保存版は保存した時点の内容のまま |
| 12 | （組織分離） | `org-b@example.com` でログインし、組織 A のレポートの URL を開く | 「SSBJレポートが見つかりません」と出て、中身は見えない |
| 13 | 操作履歴 | 詳細の「レポートの内容」から「操作履歴」を開き、操作の種類で絞り込み、CSV・Excel で出力する | 作成・更新・承認・差戻し・復元・出力が、誰がいつ行ったか分かる |

## 4. 制限事項

R1 の範囲に由来する制限は、正本を参照する。

| 制限 | 正本 |
|---|---|
| 準拠・保証をしないこと | [`ssbj-r1-scope.md`](ssbj-r1-scope.md) §1 |
| 扱わない機能（承認ロック・差分画面・自動の判断・業種ごとの出し分け・拠点別の集計など） | [`ssbj-r1-scope.md`](ssbj-r1-scope.md) §3.2 |
| OGT の算定機能の制約（対象ガス・Scope 2 の基準・GWP） | [`ssbj-r1-scope.md`](ssbj-r1-scope.md) §3.3 |
| 初回の対象外の要求（財務的影響の定量化・シナリオ分析など） | [`ssbj-r1-scope.md`](ssbj-r1-scope.md) §5.2 |
| 出力に必ず載せる注記 | [`ssbj-r1-scope.md`](ssbj-r1-scope.md) §7.2 |

試行の時点の実装による制限:

- **要求項目マスターは暫定版。** 要求 ID・項目 ID は見直すことがあり、記載ガイド・記載例はレビュー前（[`ssbj-spec.md`](ssbj-spec.md) §13「要求項目マスター」）。
- **承認・差戻しは、指定された承認者か OGT の管理者（`profiles.role = 'admin'`）だけができる。** OGT 本体はロール別の権限を使っていないため、
  管理者の設定は OGT の利用者管理に従う（デモデータでは `org-a@example.com` が管理者）。
- **レビューを依頼した本人と、依頼の後に内容を変更した人は、管理者でも承認できない。差戻しには理由が要る。** 試行では、依頼と承認を別のアカウントで行う
  （[`ssbj-spec.md`](ssbj-spec.md) §13「状態管理と承認ロック」）。
- **印刷・PDF 保存は操作履歴に残らない。** CSV・Excel の出力は残る。
- **レポートは削除できない。** 保存版を消させないため。試行で作ったレポートは、デモデータを入れ直す（`npm run db:seed:demo`）まで残る。
- **年度はレポートの作成後に変えられない。**
- **OGT の値は採用した時点で固定する。** OGT で算定し直しても自動では変わらず、変わったことを画面が知らせる。採用し直すかは利用者が決める。
- **全体テストは CI では走らない。** 試行の前にローカルで流す（§2 の 5）。
- **デモデータ（架空）でしか確かめていない。**

## 5. 反映と切り戻し

### 反映

- 直したい点は Issue にし、`ssbj` から作業ブランチを切って PR を出す。CI が通ってから `ssbj` へ Squash merge する
  （[`CONTRIBUTING.md`](../CONTRIBUTING.md)「ブランチ運用」）。
- 試行する人は `ssbj` を pull し、`npx supabase migration up --local` でマイグレーションを適用してから、開発サーバを起動し直す。
  反映後は §2 の 5 の全体テストを流し直す。

### 試行を止める条件

次のどれかが起きたら試行を止め、デモデータでの再現手順を Issue に書く。

- 他の組織のレポート・入力・保存版が見える、または変えられる
- 保存版の内容が、保存した後に変わる
- 未入力・未確認・非該当・未算定が 0 や空欄として出る
- 排出量が二重に足される（サプライヤー別の参考値が合計に入るなど）
- 内部メモ・内部記録が、開示する内容の欄に出る
- 作成から CSV までの手順のどこかが失敗する

### 切り戻し

- **コード:** 問題の入ったマージを `git revert` する PR を `ssbj` に出す（`ssbj` に直接 push しない。force push しない）。
  手元だけ一時的に戻すときは、直前のコミットを `git switch --detach <コミット>` で開く。
- **DB:** マイグレーションは追加のみで、戻すためのマイグレーションは作らない。ローカルで元に戻すときは
  `npm run db:reset:demo` で DB を作り直す（**ローカルのすべてのデータが消える**）。
- **デモデータだけを戻す:** `npm run db:seed:demo`（デモ組織のデータを入れ直す）。

## 6. 情報の区分

このリポジトリは公開されている。

| 置き場所 | 置くもの |
|---|---|
| 公開リポジトリ（Issue・PR・`docs/`） | 試行の手順、制限事項、テスト、架空のデモデータ、一般化した技術仕様、デモデータでの再現手順 |
| GitHub Project の非公開の項目 | 試行や打ち合わせで得たフィードバック、実施者・日程、外部の関係者に関する情報、実データに関する記録 |
| どこにも置かない | 認証情報（`.env.local` の値など）、実在の企業の未公開の情報 |

判断に迷う情報は公開リポジトリに置かず、非公開の項目に置いてから相談する。
