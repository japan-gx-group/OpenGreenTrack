# 法人別の排出量集計の設計

本書はR2-15の設計書です。B案として、組織の中に法人と出資関係を登録し、期間に応じて集計する構成を採用します。以下の基本方針はユーザー承認済みです。テーブルの項目と処理手順は、この方針を実装へ渡すための設計であり、レビュー対象です。法人別集計はまだ実装されていません。

データ構造の概要は[DB設計書 §5](database-design.md)、計算例は本書§6にまとめています。実装はR2-16以降で行います。

本書は暫定版です。IDEAの利用条件のうち約款から確定できない点は、§11の確認事項としてAIST Solutionsに確認します。その回答と関係者との協議を受けて改訂します。

## 1. 採用する方針

| 論点 | 決定と理由 |
| --- | --- |
| 組織と法人 | 組織はデータを分離するテナントとして残し、その中に法人を登録する。工場は既存の「拠点」を使う。法人の追加で既存のデータ分離を変えないため。 |
| 測定アプローチ | 持分割合・経営支配力・財務支配力から報告単位で選ぶ。GHGプロトコルに基づく同じ報告では一貫して適用し、工場ごとに排出量が少なくなる方法を選べないようにする。 |
| 別の企業の報告 | 別々の報告企業が異なる方法を採用してよい。企業間の報告値の合計と工場の実績の一致は、整合性の条件にしない。報告ごとに対象と取り込み方が異なるため。 |
| 支配力による除外 | 支配力がなくScope 1・2に含めない事業も、Scope 3カテゴリー15「投資」での計上要否を確認する。報告全体から自動的に除外しない。 |
| 判断と履歴 | 支配力の根拠、除外理由、測定アプローチの選択・変更理由と影響を保存する。支配力の実態は人が確認する。 |
| 実績と報告値 | 工場の持分適用前の実績を保持し、各報告に何トン取り込んだかを別に保存する。実績の変化と集計方法の変更を区別するため。 |
| 過年度 | 出資関係と拠点の所属には有効期間と版を持たせる。確定した報告は、その時点の条件と明細を保存する。現在の所属への変更で過去の報告を書き換えない。 |
| 法人未登録 | 従来どおり組織全体を1つの報告単位とする。マイグレーションで仮の法人や既存行の所属を作らない（R12）。 |
| 係数の出典とIDEA | 法人別集計の規則は、Scope 3の算定方法（直接入力、IDEAによる積上げ、今後追加する環境省のデータベースなど）によって変えない。IDEAは任意の機能で、使わない組織には影響しない。IDEA由来の値を法人の外へ渡すときは、法人・カテゴリー以上の合計値だけにする（§8.2）。逆算できない合計値は共有できるという解釈に立つためで、この解釈は§11で確認する。 |

本書の「実績」は、工場で測定・算定した持分適用前の排出量です。すべての排出量が直接測定された値であることを意味しません。測定値か推計値か、算定条件も残します。

グループ内取引の消去、別テナントとの共有・照合は対象外です。同じ報告内での明細の二重取り込みは防ぎますが、システムだけで全企業間の重複を防げるとは扱いません。

## 2. 現行データとの関係

2026年10月23日に最新の`ssbj`（34b69d3）上の関連ファイルを確認しました。以下の現行データの説明は、その内容に基づきます。

| 現行のデータ | 法人別集計での扱い |
| --- | --- |
| `organizations` | テナントとして継続。すべての新規データも`organizationId`で分離する。 |
| `locations` | 名古屋工場・福岡工場などの拠点。期間ごとの所属法人を追加する。 |
| `activity_records` | 拠点、対象期間、活動量を保持する。所属履歴を参照して法人を特定する。 |
| `emission_results` | 算定済みの実績を使う。`locationId`がない結果もあるため、すべてを拠点経由で分類できるとは扱わない。 |
| `scope3_category_emissions` / `scope3_category_methods` | 現在は組織・年度・カテゴリーごとの直接入力値と方式選択。法人別の値と方式を管理できるよう、両方の保存単位を拡張する。 |
| `supplier_emissions` | 現行では参考情報。法人を追加しても自動的に集計へ加えない。 |
| `dashboard_aggregates` | 現在の組織別集計。法人未登録の経路では継続する。法人別報告では、報告の条件を反映した共通の集計処理を使う。 |
| `ssbj_reports` / `ssbj_report_versions` | 報告の条件と保存版を拡張する。既存の親会社名・関係・持分比率・測定アプローチの欄は、法人関係の登録や集計の切替機能ではない。 |

名古屋工場と福岡工場を同じ組織内で絞り込んでいる場合、両者はテナントではなく拠点です。もし実際に別々の組織として登録されている場合は、今回の設計だけで横断集計はできません。

R1の「子会社が親会社へ提出する」利用場面では、提出先の親会社が別テナントにいることもあります。既存の親会社名の文字列を根拠に、法人レコードやテナント間の接続を自動作成しません。

参照：[database-design.md](database-design.md)、[初期スキーマ](../supabase/migrations/20260831000000_schema.sql)、[ssbj-r1-scope.md §2](ssbj-r1-scope.md)、[ssbj-spec.md §7・§13](ssbj-spec.md)、[functional-spec.md](functional-spec.md)、[idea-scope3-spec.md](idea-scope3-spec.md)。

## 3. 法人・出資関係・拠点の持ち方

### 3.1 法人

`reporting_entities`を追加します。主な項目は`id`、`organizationId`、名称、所在国、日本の法人番号、LEIです。法人番号とLEIは任意とし、未登録でも利用できます。識別子は形式を検証し、同じ組織内での重複登録を防ぎます。法人番号には国・識別子の種類を組み合わせ、名称だけで同一法人と判定しません。

海外法人の識別子にはLEIを使えますが、すべての法人がLEIを持つ前提にはしません。同じ実在法人が別テナントにも登録されることは許容します。テナントをまたぐ共通法人マスタは作りません。

法人の名称変更は同じIDのまま扱います。過去の表示名や識別子は報告の保存版に残します。

### 3.2 出資関係とその版

`entity_structure_versions`に組織内の構成の版を保存し、その版に属する`entity_relationships`に出資関係を記録します。確定した版は変更せず、取得・売却・訂正があれば新しい版を作ります。報告は使用した構成の版を指定します。

| 出資関係の項目 | 内容 |
| --- | --- |
| 参照先 | `organizationId`、`structureVersionId`、出資する法人ID、出資先法人ID |
| 関係の種類 | 連結子会社／持分法適用会社／非連結子会社／その他。出資元から見た直接の関係を保存する。 |
| 持分 | 法的な持分比率。経済的な持分が異なる場合は、その割合と根拠も保存する。 |
| 有効期間 | 開始日を含み、終了日を含まない期間。終了日なしは継続中。 |
| 根拠 | 契約・組織図などの参照、確認者、確認日、訂正理由 |

比率は0〜100％を検証し、未確認は`null`とします。未確認を0％や100％へ置き換えません。計算には浮動小数点数を使わず、DBの`numeric`と小数文字列を使います。

孫会社は出資関係をたどって表します。複数の法人から同じ会社へ出資する場合もあるため、法人テーブルに親IDを1つだけ置く方式は採用しません。単純な持分割合は経路上の割合を掛け、独立した直接・間接保有分を足します。たとえばP→Aが80％、A→Cが60％ならPのC持分は48％です。PがCを別途10％直接保有する場合は58％になります。

同じ版の同じ直接関係について、有効期間の重複を禁止します。計算に使う出資関係は循環を検出し、循環持分や経済的持分を単純な経路計算で確定できない場合は計算を止め、人の確認を求めます。結果が100％を超えたときも100％へ丸めません。循環を含む特殊な持分計算の自動化は今回の対象外です。

報告の対象期間の途中で持分比率や関係の種類が変わる場合の、期間の分け方と割合の掛け方は、本版では定めません（[#166](https://github.com/japan-gx-group/OpenGreenTrack/issues/166)）。出資関係は有効期間を持つので、後から規則を足せます。本版では、対象期間の途中で計算に使う出資関係が切り替わる報告を確定できないものとし、1つの割合で通年を計算しません。

本書でいう報告の「確定」は、報告を承認済み（`status='approved'`）にする操作です。確定できない報告では、既存の`ssbj_approval_blocker`と同じく承認を止める理由を表示します。作業中の採用や保存版の作成は止めません。構成の版の「確定」（§3.2冒頭）とは別の操作です。

### 3.3 拠点の所属

`location_entity_assignments`に`organizationId`、`structureVersionId`、`locationId`、`entityId`、有効期間を保存します。対象期間の各時点で、1つの拠点の所属法人は1つです。同じ版での重複を禁止し、所属が欠けた期間は未割当として検出します。共同支配などの判断は、所属法人とは別に報告側へ記録します。

拠点の移管日をまたぐ明細は、変更前後の期間に分けます。実測内訳がなければ、人が承認した配分方法と根拠を残します。自動の日割りは行いません。配分した実績の合計は元の明細と一致させ、その後に持分などを適用します。

所属先を変更しても元の活動量・算定結果を持分適用後の値で上書きしません。構成の旧版と報告の保存版を残すことで、売却や後日訂正によって過年度が変わることを防ぎます。

## 4. 報告単位と集計条件

### 4.1 報告の設定

既存のSSBJ報告を拡張し、報告主体の法人ID、対象期間、使用する構成の版、測定アプローチ、適用基準と版、選択理由を保持します。既存の項目は使用し、測定アプローチを重複して持たせません。報告主体は財務諸表の報告企業と整合させます。GHG排出量の対象事業は、採用した測定アプローチによって判断します。

測定アプローチは報告の設定に1つだけ持たせます。拠点・法人の明細には、方法を選ぶ欄を作りません。別企業の報告には別の方法を設定できます。比較用の試算は正式な報告と区別し、試算の合計を正式値へ混ぜません。

方法を変更するときは、変更理由、適用する期間、変更前後の比較を必須にします。確定済みの報告は上書きせず、新しい保存版として扱います。GHGプロトコル以外の測定方法が必要な場合は、適用法域と根拠を確認し、本書の3方式を無理に当てはめません。

### 4.2 人が判断する項目

報告主体から見た判断を`report_entity_assessments`に保存します。判断の対象は法人、必要ならその中の事業・拠点と期間です。同じ法人でも事業によって支配関係が異なる場合に対応するためです。

同じ報告・対象法人・対象範囲では、判断の期間の重複を禁止します。法人全体の判断を既定とし、拠点を指定した判断がある期間はそちらを優先します。各元明細に適用する判断は1つに決まる必要があり、候補が複数残る場合や未確認の場合は報告を確定できません。

| 判断 | 保存する内容 |
| --- | --- |
| 会計上の区分 | 報告主体から見て「連結会計グループ」か「その他の投資先」か。直接の出資関係の種類だけから自動確定しない。 |
| 経営支配力 | 有／無／未確認、契約などの根拠、確認者・確認日 |
| 財務支配力 | 単独支配／共同支配／支配なし／未確認、根拠、確認者・確認日 |
| 持分 | 報告主体の経済的持分、計算経路、法的持分と異なる場合の説明 |
| Scope 1・2への取り込み | 対象事業、適用割合、除外理由。割合は報告の方法と確認済みの判断から求める。 |
| カテゴリー15 | 確認待ち／計上／対象外／重要性による非開示／経過措置による非開示などの状態、適用根拠、対象投資、算定方法、確認者 |

持分比率や「連結子会社」という名称だけで、支配力を確定しません。通常の支配下の事業は支配力アプローチで100％取り込みます。GHGプロトコルの共同財務支配には持分に応じる扱いがあるため、「財務支配力なら常に0％か100％」とは実装しません。

支配力がなくScope 1・2から外すときは、カテゴリー15の確認を未完了として作成します。対象投資か、必要な算定範囲は何かを確認してから結論を保存します。投資に当たらない場合なども根拠を残し、Scope 1・2から外れた量をそのままカテゴリー15へ転記しません。

法人別報告の確定時には、必要な所属・持分・支配力・カテゴリー15の確認が完了しているか検証します。未確認や未入力は0トンと区別し、報告を確定できない理由として表示します。人が判断すべき結論を、システムの初期値で補いません。

### 4.3 集計と第52項の分解

集計は、対象期間の実績→所属法人→報告主体から見た取り込み割合の順で行います。法人単体の値と子会社込みの値を同時に足さないよう、入力は重複のない元明細にそろえます。持分の計算経路が複数あっても、その明細の取り込み割合を先に合算し、明細自体は1回だけ取り込みます。

Scope 1とScope 2はそれぞれ、取り込んだ量を「連結会計グループ」と「その他の投資先」に分けます。会計上の区分と測定アプローチは別の判断です。「持分法適用会社だから必ず30％」とは決めません。Scope 3はカテゴリー別に集計し、第52項の2区分をScope 3全体へ機械的に広げません。

共通のサーバー側処理が集計値と内訳を返し、画面やPDFが別々の式で再計算しない構成にします。数値は元の精度を保持し、中間の持分計算では丸めず、報告の表示時に丸めます。丸めた法人別表示の和と合計に差が出た場合は、丸め差を表示します。

### 4.4 拠点のないデータとScope 3

拠点のない直接入力には、帰属先の法人IDを指定します。`scope3_category_emissions`と`scope3_category_methods`は、組織・法人・年度・カテゴリーを対応させ、法人別の入力値と方式選択が食い違わないようにします。既存の組織単位の行は残し、法人別の行との混在を黙って合計しません。

法人別集計へ切り替えるときは、既存の直接入力と拠点なしの算定結果の帰属を確認します。自動的に親会社へ付けたり、架空の拠点を作ったりしません。配分が必要なら、元データと法人別の配分量・根拠を記録し、二重計上を防ぎます。未割当のデータがある報告は確定できません。

カテゴリー15を投資先の実績から算定する場合、その値と同じ対象の直接入力値を両方足しません。直接入力か算定かを明示し、対象投資と期間で重複を確認します。Scope 3の範囲や持分の扱いはカテゴリー別の算定規則に従います。Scope 1・2向けの取り込み割合を、すべてのScope 3データに一律で掛ける設計にはしません。

同じカテゴリーで法人ごとに算定方式が異なる場合（P社は直接入力、A社は積上げなど）、グループの採用値には法人ごとの方式・採用値・充足状況を保持し、カテゴリーの方式は「混在」として表します。既存の採用値の方式（`direct`／`calculated`の二択、[ssbj-spec.md §7](ssbj-spec.md)）はそのまま読めるようにします。含める法人に未入力・未算定がある場合は、カテゴリー全体を算定済みとしません。積上げの充足件数は、積上げを採用する法人の件数を合算します。

## 5. 実績から報告値をたどるための保存

法人別集計の値を報告へ採用するときは、既存の`ssbj_ogt_adoptions`を拡張し、集計条件、構成の版、判断の内容、取り込み明細を一緒に保存します。保存版はその採用内容を`ssbj_report_versions`のスナップショットへ固定し、スキーマの版を付けます。採用後に元データや集計条件が変わった場合は再採用を必要とし、古い明細に新しい条件を組み合わせて確定しません。元の算定結果は再計算で更新・削除され得るため、IDだけの保存では足りません。

各取り込み明細には次の情報を残します。

| 情報 | 例 |
| --- | --- |
| 報告 | P社の2026年度報告、保存版3、持分割合 |
| 元データ | 算定結果ID、活動量ID、拠点ID、所属法人ID、対象期間、元データの版または取得時点 |
| 計算の入力 | 持分適用前の排出量、単位、元のScope、活動量・係数・GWPなどの算定根拠、期間を分けた場合の配分量 |
| 取り込みの根拠 | 構成の版、判断ID、その時点の判断内容・根拠資料の版、確認者 |
| 取り込み先 | Scope、カテゴリー、会計上の区分、取り込み割合、取り込んだ排出量 |
| 除外・非開示 | 対象量、理由、適用基準、確認状況。未確認・真のゼロ・非開示を区別する。 |

画面では、合計→法人→拠点→元明細と取り込み根拠をたどれるようにします。拠点のない直接入力は、法人から直接その明細へ移ります。除外された明細も確認できるようにします。ただし、IDEA由来の値は、保存版の中では法人・カテゴリーの合計までしかたどれません（§8.2）。

IDEA由来の値だけは、上の表と扱いを変えます。

- 採用値と保存版には、報告主体自身の分も含めて、IDEA由来の明細を複写しません。法人・Scope 3カテゴリーごとの合計値と件数、元の算定結果のID、算定に使った版・GWPモデル・引用表記だけを保存します。保存版はプレビュー・履歴・出力がそのまま読むので、明細を入れなければ閲覧者ごとに判定する必要がありません。元の算定結果が再計算・削除されると明細まではたどれなくなりますが、約款の条件を優先してこの制限を受け入れます。
- 印刷・PDF・Excel・CSVの出力には、係数・活動量・明細ごとの排出量を含めず、IDEAを使ったカテゴリーと出典（版・GWPモデル・引用表記）を明記します（約款 第7条の2第2項）。

同じ保存版・元明細・対象期間・取り込み先への重複登録を防ぎます。期間や帰属を分割したときは配分先も識別し、合計の検証を行います。この検証の範囲は同じ報告内です。異なる報告の値を合計して元明細と一致させる制約は置きません。

確定処理では報告の改訂番号を確認し、構成・実績・判断を一貫した時点で取得して保存します。読み取り中に変更があれば再計算を求めます。承認後の編集制限と保存版の復元は、既存の報告管理の規則に合わせます。

## 6. 計算例

### 6.1 親会社・子会社・孫会社

すべて架空の通年データです。持分と所属は期中に変わらず、法的持分と経済的持分は一致するものとします。数値はScope 1、単位はt-CO2eです。Scope 2は別に同じ考え方で集計します。

1つのテナントにP・A・B・C・Dを登録します。Pの名古屋工場が100、福岡工場が200なので、P自身の実績は300です。PはAの80％、Bの60％、Dの30％を保有し、AはCの60％を保有します。A・B・Cは連結子会社、Dは持分法適用会社です。

PグループはP・A・B・Cの事業に経営支配力と財務支配力を持つとします。Dの事業には契約上の経営支配力がありますが、財務支配力はありません。共同財務支配はない例です。

| 法人・拠点 | 実績 | Pの持分 | 持分割合で取り込む量 | 経営支配力で取り込む量 | 財務支配力で取り込む量 |
| --- | ---: | ---: | ---: | ---: | ---: |
| P：名古屋・福岡 | 300 | 100％ | 300 | 300 | 300 |
| A：大阪 | 300 | 80％ | 240 | 300 | 300 |
| C：仙台（孫会社） | 400 | 48％ | 192 | 400 | 400 |
| B：広島 | 200 | 60％ | 120 | 200 | 200 |
| D：横浜 | 500 | 30％ | 150 | 500 | 0 |
| 合計 | 1,700 | — | 1,002 | 1,700 | 1,200 |

Cの持分は80％×60％＝48％なので、持分割合では400×48％＝192です。支配力がある2方式では400を取り込みます。3列は比較用であり、報告には選んだ1列を採用します。

| 第52項の区分 | 持分割合 | 経営支配力 | 財務支配力 |
| --- | ---: | ---: | ---: |
| 連結会計グループ：P・A・B・C | 852 | 1,200 | 1,200 |
| その他の投資先：D | 150 | 500 | 0 |
| 合計 | 1,002 | 1,700 | 1,200 |

財務支配力でDが0になるのは、このScope 1の表での扱いです。Dへの投資についてカテゴリー15の計上要否を確認する処理は残ります。

別の所属例として、2工場だけを比べます。名古屋100がP、福岡200が80％子会社Aの所属なら、Pの持分割合による報告値は100＋200×80％＝260です。両工場ともP所属なら300です。どちらも工場の実績合計は300のままです。

### 6.2 別々の企業が同じ工場を報告する場合

X社とY社がT社を30％・70％保有し、T社の唯一の工場のScope 1実績が100、Scope 2実績が0とします。Xが契約に基づく経営支配力を持つことを確認済みとします。

| 報告企業 | 採用する方法 | この工場からScope 1へ取り込む量 |
| --- | --- | ---: |
| X社 | 経営支配力 | 100×100％＝100 |
| Y社 | 持分割合 | 100×70％＝70 |

別々の報告の値を足すと170ですが、工場の実績100との一致は求めません。異なる報告を合算して物理的な排出量を求める用途には使えないためです。この例は報告の考え方を示すもので、テナント間で同じ実績を共有・照合する機能を含みません。

### 6.3 Scope 1・2から外した後のカテゴリー15

前例とは別に、Xが財務支配力を採用し、Tへの財務支配力がない場合を考えます。XのScope 1・2には取り込みませんが、カテゴリー15の確認が必要です。

Tへの株式投資がカテゴリー15の算定対象で、通年の持分が30％、投資先のScope 1が100、Scope 2が0、追加のScope 3の算入が必要となる条件はないと確認できた例では、投資先別の算定値は（100＋0）×30％＝30です。投資先のScope 3が重要な場合など、追加の算入範囲も確認します。除外した100をそのまま転記する計算ではありません。

適用基準・重要性・経過措置による非開示を判断した場合は、その根拠と対象期間を残します。「未確認」「非開示」「排出量が0」を同じ数値に置き換えません。

### 6.4 集計方法を変えた影響

工場の実績100とXの持分30％が変わらないまま、Xが持分割合から経営支配力へ変更すると、この工場のScope 1取り込みは30から100へ変わります。差の70は方法変更による増加です。工場の排出量が70増えたことを意味しません。

変更影響は、同じ実績・所属・持分・支配関係を固定し、変更前と変更後の方法で計算して示します。Scopeとカテゴリーごとの増減を保存し、カテゴリー15への影響も別に確認します。前年との差には活動量、係数、取得・売却、方法変更などが含まれるため、方法変更以外の差をすべて「実際の排出削減」と表示しません。要因を区別できない部分は未分解として残します。

## 8. 既存組織の利用・権限・IDEA由来のデータ

### 8.1 既存組織と権限

法人未登録の組織は従来の経路で集計します。法人を登録しただけで過去の報告や既存データを自動変換しません。法人別報告への切替時に、所属、拠点なしデータ、集計条件の確認を行い、切替後の報告から使用します。既存の保存版はそのまま参照できます。

新しいテーブルは同じ組織内のIDだけを参照できるようにし、RLSと複合外部キーなどでテナントの一致を検証します。組織IDや法人IDを画面から受け取っただけでは権限を認めません。

[権限表 §1〜§3](authorization-matrix.md)の「組織×利用者×ロール」に任意の法人IDを追加する方針に合わせます。法人IDなしは組織全体、法人IDありは指定法人を対象とします。法人の権限は子会社へ自動継承しません。管理者の組織全体の権限を維持し、入力担当・承認担当・閲覧者の操作範囲と閲覧できる保存版は権限表に従います。

グループ報告では、報告主体の法人に対するロールの確認に加え、含まれる各法人のデータを閲覧・利用する権限も確認します。拠点のない直接入力や取り込み明細も対象です。閲覧者に承認前の報告や未承認の保存版を見せません。自己承認禁止は管理者にも適用し、レビュー依頼者と依頼後の編集者は承認できないものとします。

権限表の「ロール未割当は入力担当」という互換動作は、法人範囲の制限を迂回する根拠にしません。法人限定の権限を適用する利用者について、範囲外の法人を未割当の組織全体の入力担当として扱うことを禁止します。既存の組織全体の利用者を法人限定へ切り替えるときは、組織全体の権限との重複を確認します。

法人の範囲はRLS、Route Handler、RPC、採用・保存・出力の各経路で検証します。現行のOGT本体の権限体系は、§8.2のIDEA由来の行を除き、この設計だけで法人別に変更するものではありません。全画面・API・RLSへの適用が済むまでは「法人単位で全データが分離される」と説明しません。

### 8.2 IDEA由来のデータ

IDEAは、利用企業が自らライセンスを契約して取り込む任意の係数です（[既存仕様 §0](idea-scope3-spec.md)）。Scope 3を直接入力だけで扱う組織や、IDEA以外の係数で積み上げる組織には、本節は関係しません。本節の規則は、IDEA由来の値が法人の境界を越える場面だけに適用します。

IDEA由来かどうかは、元の活動量が積上げ用の種別（`activity_records.energyType='scope3_activity'`）かどうかで判定します。この種別はIDEAの積上げだけに使い、係数の作成画面や係数CSVの取込の対象から外されています（[機能仕様 §3](functional-spec.md)）。係数が削除されて`ideaFactorId`が空になっても判定は変わりません。`scope='scope3'`や`appliedFactor*`の有無では判定しません。公式係数によるScope 3（廃棄物・出張・通勤など）やScope 1・2の算定結果も`appliedFactor*`を持つためです（[算定ロジック §4](calculation-logic.md)）。既存仕様 §8-1が`emission_results`の`scope='scope3'`の行を一律に自組織限定にしている点は、この判定に合わせて見直します（[#171](https://github.com/japan-gx-group/OpenGreenTrack/issues/171)）。ライセンスの制約がない係数で積み上げる仕組みを追加するときは、行ごとに係数の出典を持たせて判定します。

約款とAIST Solutionsの公開資料で確認した内容は次のとおりです（2026年10月22日確認）。

| 確認した内容 | 根拠 |
| --- | --- |
| IDEAデータを第三者へ開示・譲渡・貸与できない。第三者には使用者の子会社・関連会社を含む。 | 約款 第3条第1項前段 |
| IDEAデータを含む計算結果を閲覧できるのは、同一社内・同一組織の構成員に限る。原単位の閲覧と計算への使用は登録取扱者に限る。 | 約款 第3条第1項後段 |
| 逆算して原単位を推測できるデータは「修正データ」で、IDEAデータに含まれる。原単位と活動量を組み合わせた算定結果は「派生データ」。 | 約款 第1条第3〜5項 |
| 逆算して原単位を推測できない結果は、環境報告書などに記載して公表できる。公表時はIDEAを使って算出した箇所を明記する。 | 約款 第7条の2、FAQ |
| 子会社がIDEAのライセンスを保有していれば、算定に使った係数の数値を子会社へ共有できる。 | AIST Solutions FAQ |

既存仕様 §8-1の「別法人である子会社へは計算結果すら共有できない」は約款の文言ではありません。明細には当てはまりますが、逆算できない合計値まで共有できないとは約款から読み取れません。

法人の境界を越えてIDEA由来の値を渡す範囲を、次の3段階で定めます。

| 段階 | 法人の外へ渡す範囲 | 前提とする解釈 |
| --- | --- | --- |
| 0 | 渡さない | 計算結果は合計値も共有できない |
| 1（本版で採用） | 法人・Scope 3カテゴリー以上の合計値 | 逆算できない値は、公表できるのと同様に渡せる |
| 2（後続） | 明細も渡す。ただし受け取る法人のIDEAライセンスを確認済みの場合に限る | ライセンス保有者どうしなら共有できる（FAQ） |

本版は段階1を採用し、次の規則を置きます。

- **明細は契約法人の外へ出さない。** IDEA由来の明細（活動量・係数・明細ごとの排出量と拠点別の内訳）を閲覧・利用できるのは、算定に使った取込の契約法人に所属する利用者だけです。所属は、利用者が雇用されている法人として管理者が登録し、確認者と確認日を残します。SSBJのロールは操作の範囲を表すもので、所属の代わりにはなりません。子会社の範囲のロールを親会社の担当者に付けても、子会社のIDEA明細は見えません。組織全体のロールでも同じです。
- **他の法人へは合計値だけを渡す。** 渡すのは、法人・Scope 3カテゴリーごと、またはそれより大きい単位の合計値です。合計が1件の明細だけからなる場合は明細の排出量と同じ値になりますが、活動量を渡さないので、システムの中では原単位を求められません。受け取る側がシステムの外で活動量を知っている場合までは防げないため、この扱いは§11で確認します。
- **現在のデータを直接読む経路にも同じ制御をかける。** 活動量の一覧、Scope分析の明細（`scopeAnalysisService`）、算定結果、`idea_imports`・`idea_factors`は、ブラウザからRLSで直接読まれます。法人を登録した組織では、これらのIDEA由来の行を、上の条件を満たす利用者にだけ返します。ただし、現行のScope分析とカテゴリー集計のRPCは、こうした明細から合計を計算しています。明細のRLSだけを絞ると、カテゴリーの合計が0になり総計と合わなくなります。そのため、法人別のRLSを適用するときに、Scope分析とダッシュボードのカテゴリー合計・充足件数も、許可された単位の合計を返すサーバー側の処理から取るように改めます。
- **取込と算定結果は契約法人に属させる。** 法人を登録した組織では、IDEAの取込（有効・無効を問わない）にライセンスを契約した法人を持たせます。算定結果は、算定時に使った取込の契約法人に属します。拠点の移管や構成の版の訂正があっても、明細を閲覧できる人は変わりません。係数の検索・選択と積上げ算定は、契約法人に所属する利用者と、算定の時点で契約法人に属する拠点の活動量に限ります。版の更新による係数の付け替えも、契約法人が同じ取込どうしに限ります。ほかの法人のScope 3は、直接入力かIDEA以外の係数で扱います。組織で有効な取込を1件に限る現行の制約は変えません。法人別集計へ切り替えるときは、既存の取込と算定結果の契約法人を利用者が確認して登録します。確認されていない取込と算定結果の明細は、だれにも返しません。
- **合計から明細へたどる画面**では、閲覧できないIDEA由来の値を法人・カテゴリーの合計で止め、「ライセンスの条件により明細を表示しない」と示します。0や未入力とは区別します。
- **有効にする条件。** 法人を登録した組織でIDEAの積上げを使えるのは、上の経路すべてに法人別の制御を適用し、明細を見られない利用者に見せるカテゴリー合計が総計と一致すると確かめた後です。法人を登録しない組織と、IDEAを使わない組織は、これまでどおり使えます。

段階2では、法人ごとに「IDEAライセンスの保有を確認済み」という記録（対象の版、有効期限、確認者、確認日）を足し、確認済みの法人に所属する利用者にも明細を見せます（[#168](https://github.com/japan-gx-group/OpenGreenTrack/issues/168)）。法人ごとに取込を分けるか、同じ版のライセンスを持つ法人どうしで1つの取込を共用するかも、§11の回答を受けてそこで決めます。回答が段階0なら、他の法人のIDEA由来の値は合計値も取り込まず、「ライセンスの条件により除外」として扱います。どちらの場合も、段階1の保存版と集計の形は変わりません。

- テナントをまたぐ参照を拒否し、法人未登録の既存組織は従来どおり利用できること。
- 対象期間の途中で出資関係が切り替わる報告を確定できないこと。
- IDEAを使わない組織で、集計結果と画面が変わらないこと。
- 公式係数によるScope 3（廃棄物・出張・通勤など）とScope 1・2の算定結果が、IDEA由来として扱われないこと。
- 契約法人に所属しない利用者（子会社の範囲のロールを付けた親会社の担当者、組織全体のロールだけを持つ利用者を含む）に、IDEA由来の明細と拠点別の内訳が活動量の一覧・Scope分析・算定結果・係数のどこにも返らず、法人・カテゴリー以上の合計値だけが見えること。その合計が総計と一致すること。
- 拠点の移管や構成の版の訂正の後も、算定済みのIDEA明細の閲覧先が変わらないこと。
- 採用値と保存版にIDEA由来の明細と拠点別の内訳が入らず、法人・カテゴリーごとの合計値・件数・出典（版・GWPモデル・引用表記）が入ること。元の算定結果を再計算・削除しても、保存版の合計値と出典が変わらないこと。
- 出力に係数・活動量・明細ごとの排出量が含まれず、IDEAを使ったカテゴリーと出典が明記されること。
- 法人ごとに算定方式が違うカテゴリーが「混在」となり、未入力・未算定の法人があると算定済みにならないこと。
- 同じ明細に法人全体と拠点の判断が重なるとき拠点の判断が使われ、候補が1つに決まらない場合は承認できないこと。

R2-15の完了条件は、必要な設計判断と理由、計算例がそろい、作業者以外の2人によるレビューと指摘の解決が完了していることです。PR・CI・lint・build・`ssbj`への統合は、このIssueの完了条件に含めません。リポジトリへ変更を取り込む場合は、別途、共通のコミット・PR・マージ規約に従います。

## 11. AIST Solutionsへの確認事項

§8.2の段階を決めるため、次の点をAIST Solutionsに確認します。回答によって§8.2の採用段階を改訂します。

1. 子会社が自らのライセンスで算定した、逆算できない合計値（Scope 3カテゴリー別のt-CO2eなど）を、親会社の連結開示のために親会社へ渡してよいか。親会社がライセンスを持たない場合も同じか。合計が1件の明細だけからなる場合（活動量は渡さない）も同じか。
2. 親会社と子会社がそれぞれライセンスを持つ場合、IDEA由来の明細を同じシステムの中で共有してよいか。同じ版のライセンスを持つ法人どうしで、1つの取込を共用してよいか。
3. 連結のGHG開示（SSBJ）のための子会社のScope 3算定と親会社への報告を、サプライチェーンライセンスの事業目的として承認してもらえるか。公開資料の例は製品CFPと国のプロジェクトで、組織のGHG排出量は挙がっていない。
4. 利用企業が自社でOGTを導入・運用する場合を、算定システムの申請が不要な「自社内限定のシステム」として扱ってよいか。
