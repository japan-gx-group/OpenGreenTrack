# SSBJ 開示レポート R2 の試行手順（R2-14）

チームがローカル環境とデモデータで R2 を試すための、準備・手順・制限事項・反映と切り戻し・情報の区分をまとめる。
R1 の試行手順（T15）を、R2 で加わった機能に合わせて更新したもの。この文書は「R2 をどう試すか」を正とする。
R1 で何を扱うかは [`ssbj-r1-scope.md`](ssbj-r1-scope.md)、データ契約と保存の仕組みは [`ssbj-spec.md`](ssbj-spec.md)、
ロールで何ができるかは [`authorization-matrix.md`](authorization-matrix.md) を正とし、ここでは繰り返さない。

> R1・R2 は社内確認用の試行版であり、SSBJ 基準への準拠の認定・第三者保証・対外提出の完了を意味しない
> （[`ssbj-r1-scope.md`](ssbj-r1-scope.md) §1）。試行の結果を、準拠を確認した成果物として扱わない。

---

## 1. 試行の範囲

| 項目 | 内容 |
|---|---|
| 環境 | ローカル（Docker 上のローカル Supabase と、`ssbj` ブランチの開発サーバ） |
| データ | デモデータ（架空の組織・ユーザー・排出量）で試す。実際の企業のデータで試すかどうかと、その環境は、この文書の範囲外（§6 の非公開の項目で決める）。実際の企業のデータで試すときも、先に §2 の 5 の全体テストがすべて通っていることを条件にする |
| 実施者 | チーム |
| R2 で加わった機能 | 自己承認の禁止と差戻しの理由（R2-08）、SSBJ のロール（入力担当・承認担当・閲覧者。R2-09〜R2-12）、外部で算定した排出量（R2-13） |
| ほかの担当者の R2 の機能 | `ssbj` に入った時点で、各 Issue がこの文書に手順と制限事項を足す（業種の候補・一覧での判断・選択式テンプレート（R2-01〜R2-03）、方式案（R2-04）、ファイルの SHA-256（R2-22）、返却と削除（R2-24）も `ssbj` に入っている。使い方は [`ssbj-spec.md`](ssbj-spec.md) §13 の各節） |

**R2 を実際の企業のデータで使う前に、全体テストで次の 4 つの条件を確かめる**（どの手順で確かめているかは
[`ssbj-spec.md`](ssbj-spec.md) §13「R2 の全体テスト（R2-14）」）。

1. 権限の無い操作が必ず拒否される（画面・API・PostgREST の直接呼び出しのどこからも）
2. 数値が合う（OGT の算定値と外部算定値を二重に計上しない）
3. 根拠を辿れる（外部算定値から、根拠文書・算定した者・確認者・操作履歴まで）
4. 承認した内容が後から変わらない（自己承認の拒否、元データ・根拠・拠点名を変えた後の保存版）

## 2. 準備

1. `ssbj` を最新にする（`git switch ssbj` → `git pull`）。依存が変わっていれば `npm ci`。
2. ローカル Supabase を起動し、マイグレーションを適用する（`npx supabase start` → `npx supabase migration up --local`）。
   初めて動かす場合の手順は [`setup-guide.md`](setup-guide.md) を参照。
3. デモデータを入れる（`npm run db:seed:demo`）。
   - `supabase/seeds/demo/` の `demo.sql`（デモ組織・ユーザー・排出量）と `ssbj_demo.sql`（入力例の入った SSBJ レポート、SSBJ のロールの利用者、外部算定値の例）が流れる。
   - **デモ組織のデータは消してから入れ直す。** 手元でデモ組織に入力した内容は消える。DB 全体を作り直すときは
     `npm run db:reset:demo`（ローカルのすべてのデータが消える）。
4. 開発サーバを起動する（`npm run dev` → http://localhost:3000）。
5. **試行の前に全体テストを流し、すべて通ることを確かめる**（`npx playwright test -c playwright.ssbj.config.ts`。
   R1 の 26 手順と R2 の 11 手順が流れる。前提・確認している内容は [`ssbj-spec.md`](ssbj-spec.md) §13「R1 の全体テスト（T14）」
   「R2 の全体テスト（R2-14）」）。通らなければ試行しない。

使うアカウント（デモデータの公開パスワード。`supabase/seeds/demo/demo.sql`・`ssbj_demo.sql`）:

| アカウント | 組織 | SSBJ のロール | 使いどころ |
|---|---|---|---|
| `org-a@example.com` / `password123` | 架空精密工業株式会社 | 管理者（環境 太郎。OGT の管理者） | 試行の本体。2024 年度に OGT の算定値・Scope 3 の直接入力・サプライヤー別排出量と、入力例の入った SSBJ レポートがある。ロールの割り当て |
| `member-a@example.com` / `password123` | 架空精密工業株式会社 | 入力担当（算定 花子。割り当て無し） | 入力 |
| `member3-a@example.com` / `password123` | 架空精密工業株式会社 | 承認担当（確認 三郎。`ssbj_demo.sql` で追加） | 承認・差戻し |
| `member2-a@example.com` / `password123` | 架空精密工業株式会社 | 閲覧者（報告 次郎） | 承認した保存版の閲覧 |
| `org-b@example.com` / `password123` | 架空ロジスティクス株式会社 | 管理者 | 組織分離の確認（組織 A のレポートが見えないこと） |

SSBJ のロールは「SSBJ の権限」（`/ssbj/roles`）で確かめ、管理者（`org-a@example.com`）が変えられる。
承認担当は内容を見られるが編集はできず、閲覧者は承認済みのレポートの承認した保存版だけを、内部メモ・内部記録を除いて見られる。ロールで何ができるかは
[`authorization-matrix.md`](authorization-matrix.md) を正とする。

### 根拠のファイルの照合

根拠のファイルが、記録したときと同じものかを確かめる。ファイルはこの端末の中で読むだけで、アップロードも保存もしない。
照合は何も保存しないため、承認済みのレポートでもできる。

1. 根拠文書の画面で、ファイルを記録した根拠の「照合」を押す
2. 「照合するファイル」で、保管先から取り出したファイルを選ぶ
3. 結果を確かめる
   - 「一致しました」: 記録したときと同じ内容のファイル（ファイル名が違っても、中身が同じなら一致する）
   - 「一致しません」: 違うファイルか、中身が変わっている。保管先での版 ID・保存担当を手がかりに、記録したときのファイルを探す。
     見つからないときは、根拠文書の記録を見直す（承認済みなら差戻してから）
4. 試行では、記録したファイルを 1 文字だけ書き換えて保存し直したものを選び、「一致しません」と出ることも確かめる

画面を https でない社内のアドレス（`http://192.168.…` など）で開くと、ブラウザの制限で SHA-256 を計算できない。`localhost` か https のアドレスで開く。

## 4. 制限事項

R1 の範囲に由来する制限は、正本を参照する。

| 制限 | 正本 |
|---|---|
| 準拠・保証をしないこと | [`ssbj-r1-scope.md`](ssbj-r1-scope.md) §1 |
| 扱わない機能（差分画面・自動の判断・業種ごとの出し分け・拠点別の集計など） | [`ssbj-r1-scope.md`](ssbj-r1-scope.md) §3.2 |
| OGT の算定機能の制約（対象ガス・Scope 2 の基準・GWP） | [`ssbj-r1-scope.md`](ssbj-r1-scope.md) §3.3 |
| 初回の対象外の要求（財務的影響の定量化・シナリオ分析など） | [`ssbj-r1-scope.md`](ssbj-r1-scope.md) §5.2 |
| 出力に必ず載せる注記 | [`ssbj-r1-scope.md`](ssbj-r1-scope.md) §7.2 |

試行の時点の実装による制限:

- **要求項目マスターは暫定版。** 要求 ID・項目 ID は見直すことがあり、記載ガイド・記載例はレビュー前（[`ssbj-spec.md`](ssbj-spec.md) §13「要求項目マスター」）。
- **SSBJ のロールは SSBJ の中だけで効く。** OGT 本体（データ入力・算定・設定など）は、これまでどおり同じ組織の利用者なら誰でも操作できる
  （[`authorization-matrix.md`](authorization-matrix.md) §4）。OGT の管理者は、SSBJ でも割り当てに関係なく管理者になる。
- **ロールを割り当てていない利用者は入力担当。** 管理者のいない組織ではロールを割り当てられない（[`authorization-matrix.md`](authorization-matrix.md) §5）。
- **閲覧者が見られるのは、承認済みのレポートの「今の」承認した版だけ。** 差戻すと、そのレポートは閲覧者に見えなくなる。
- **レビューを依頼した本人と、依頼の後に内容を変更した人は、管理者でも承認できない。差戻しには理由が要る。** 試行では、依頼と承認を別のアカウントで行う
  （[`ssbj-spec.md`](ssbj-spec.md) §13「状態管理と承認ロック」）。
- **外部算定値は、出典と確認者を記録するだけで、値そのものの正しさは確かめない。** 算定方法と根拠文書の中身の確認は、確認者が行う。
  単位は t-CO2e だけで、GWP の換算は外部で済ませた値を入れる。
- **OGT の値と外部算定値は足し合わせない。** Scope ごとの合計や連結の集計はまだ無い（R2-20）。Scope 2 の外部算定値（基準別）は、
  OGT の値と別の値として示す。OGT の同じ基準の値が算定済みなら、CO2 を含む Scope 2 の外部算定値は二重計上として拒否される
  （[`ssbj-spec.md`](ssbj-spec.md) §13「外部で算定した排出量（R2-13）」、§7.2）。
  - 基準別の値を取り込む前に、CO2 を含む Scope 2 の外部算定値を入れたレポートでは、OGT の値を採用し直すと、その基準の OGT の値が算定済みなら
    採用全体が拒否される（Scope 1・Scope 3 の値も更新されない）。採用し直す前に、その外部算定値を消すか、対象ガスから CO2 を外す。
    画面の「OGT の値が変わりました（Scope 2 の基準別の値）」は、この採用し直しを促す知らせ。
- **印刷・PDF には、内部メモ・内部記録を出さない。** 「内部メモも表示する」は画面のプレビューにだけ効く（印刷の URL に `internal=1` を付けても出ない）。
  全体テストの手順 8 で確かめる。閲覧者には、画面・CSV・Excel のどれでも出さない（手順 10）。
- **印刷・PDF 保存は操作履歴に残らない。** CSV・Excel の出力は残る。
- **レポートは削除できない。** 保存版を消させないため。試行で作ったレポートは、デモデータを入れ直す（`npm run db:seed:demo`）まで残る。
- **年度はレポートの作成後に変えられない。**
- **OGT の値は採用した時点で固定する。** OGT で算定し直しても自動では変わらず、変わったことを画面が知らせる。採用し直すかは利用者が決める。
- **全体テストは CI では走らない。** 試行の前にローカルで流す（§2 の 5）。
- **根拠のファイル本体は保存しない。** 記録するのは SHA-256 などの値だけ。照合するときは、手元に同じファイルを用意する。
- **デモデータ（架空）でしか確かめていない。**

## 5. 反映と切り戻し

### 反映

- 直したい点は Issue にし、`ssbj` から作業ブランチを切って PR を出す。CI が通ってから `ssbj` へ Squash merge する
  （[`CONTRIBUTING.md`](../CONTRIBUTING.md)「ブランチ運用」）。
- 試行する人は `ssbj` を pull し、`npx supabase migration up --local` でマイグレーションを適用してから、開発サーバを起動し直す。
  反映後は §2 の 5 の全体テストを流し直す。

### 試行を止める条件

次のどれかが起きたら試行を止め、デモデータでの再現手順を Issue に書く。

- 他の組織のレポート・入力・保存版が見える、または変えられる
- ロールで許されていない操作ができる（承認担当・閲覧者が作業中の内容を変えられる、閲覧者に承認前のレポートや作業中の内容が見える、自分の依頼を承認できる）
- 保存版の内容が、保存した後に変わる
- 未入力・未確認・非該当・未算定が 0 や空欄として出る
- 排出量が二重に足される（サプライヤー別の参考値が合計に入る、同じ排出量が OGT の値と外部算定値の両方に入るなど）
- 外部算定値の出典（根拠文書・算定した者・確認者）を辿れない
- 内部メモ・内部記録が、開示する内容の欄に出る
- 作成から CSV までの手順のどこかが失敗する

### 切り戻し

- **コード:** 問題の入ったマージを `git revert` する PR を `ssbj` に出す（`ssbj` に直接 push しない。force push しない）。
  手元だけ一時的に戻すときは、直前のコミットを `git switch --detach <コミット>` で開く。
- **DB:** マイグレーションは追加のみで、戻すためのマイグレーションは作らない。ローカルで元に戻すときは
  `npm run db:reset:demo` で DB を作り直す（**ローカルのすべてのデータが消える**）。
- **デモデータだけを戻す:** `npm run db:seed:demo`（デモ組織のデータを入れ直す。SSBJ のロールの割り当ても戻る）。
- **SSBJ のロールの割り当てだけを戻す:** 管理者が「SSBJ の権限」で戻す（入力担当に戻すときも行は消さない。変更は記録に残る）。
