# SSBJ 根拠資料の取込みから根拠記録と文章の下書きを作る方式案（R2-04・方針検討）

> 位置づけ: R2-04 の方針検討の成果物。**実装の仕様ではない。** 採用する方式と、実装の前に決める方針を判断するための材料。
> この文書を理由に、コード・DB・ストレージ・外部サービスの契約は変えない（R2-04「今回の対象外」）。
> 前提とした現状は `ssbj` ブランチ（2026-10-22 時点。#59・#64〜#66・#74・#75・#90 の取込み後）。
> 2026-10-29 に `main` を取り込み、OGT 本体で決まった AI の扱い（Issue #3 の方針と共通の入口）と、活動量の記録の帳票の保存に合わせて、
> §1・§3.4〜§3.6・§4〜§6 を改めた。AI の扱いの正本は [`architecture.md`](architecture.md) の「AI 連携」。

## 1. 今の仕組み（調べた範囲）

| 対象 | 今の状態 |
|------|----------|
| 根拠文書の保存 | `ssbj_evidence`（`20260929150000_ssbj_evidence.sql`）。項目 ID ごとに複数件。資料名・版・保管先・参照位置・主管部署は**内部記録**、開示用参照文だけが開示側（`docs/ssbj-spec.md` §5） |
| 根拠文書の画面 | `SsbjEvidencePage.client.tsx`。利用者が文字で登録・編集・削除する。**ファイルは扱わない** |
| 取得・保存 | `evidenceService.ts`（ブラウザの Supabase クライアント＋RLS）、`useSsbjEvidence.ts`、入力の正規化・検証は `utils/evidence.ts` |
| 要求項目マスター | `requirementMaster.ts`。**暫定版**（`SSBJ_REQUIREMENT_MASTER_VERSION`）。要求 ID → 入力先（文章の項目 ID など）の対応を持つ。確定は #49 |
| 操作履歴 | `ssbj_audit_logs`（#59）。SSBJ の行の作成・更新・削除をトリガーで記録し、書き換えない |
| ファイル保管 | OGT 本体の `import-files` / `upload-quarantine` バケット（`20260831000003_storage.sql`）。パス先頭＝組織 ID で分離。SSBJ からは使っていない。本体は活動量の記録の根拠の帳票（請求書など）を `import-files/<組織ID>/activity-evidence/` に保存し、行を `activity_evidence_files`（サーバが中身を確かめた SHA-256・形式・大きさ）に持つ（`20261026120000_activity_evidence.sql`。消すのはサーバだけ） |
| ファイルの同一性 | R2-22（#90 で ssbj に取込み済み）で、ブラウザ内で SHA-256 を計算して記録する（`ssbj_evidence."fileSha256"`）。**ファイル本体はアップロードしない** |
| AI 利用 | SSBJ ではまだ使っていない。OGT 本体は Issue #3 の方針（2026-10-24）で、AI の共通の入口（`src/lib/ai/` の `generateStructured`）を作った。鍵は組織単位で管理者だけが設定し、用途の登録・送る前の確認・回数の上限・監査ログ（`system_audit_logs` の `ai.request`）を共通にする。請求書の読取りが最初の用途 |

## 2. 方式の比較

「資料をどこに置くか」と「内容をどう抜き出すか」で、次の 4 案に分けた。

| | A. 参照の記録だけ | B. ブラウザ内の抽出 | C. 保管＋手動の対応付け | D. 保管＋AI による抽出・下書き |
|---|---|---|---|---|
| 概要 | 今の T10＋R2-22。資料は社内の保管先に置いたまま、資料名・版・SHA-256 と参照位置を記録 | 利用者が選んだファイル（テキスト・PDF のテキスト層）をブラウザ内で読み、抜き出した箇所を利用者が選んで根拠記録に貼る。ファイルは送らない | ファイルを OGT のストレージに保管し、利用者が該当箇所を選んで要求項目と対応付ける | C に加え、資料を外部 AI に送って、要求項目ごとの抜き出しと下書きの候補を作る |
| 取込み対象 | なし（記録のみ） | テキスト・PDF（テキスト層のあるもの） | PDF・Office・画像 | C と同じ＋スキャン画像（OCR） |
| 利用者の操作 | 資料名・参照位置を手で書く | ファイルを選ぶ → 箇所を選ぶ → 確認して保存 | アップロード → 箇所を選ぶ → 要求項目に対応付け | アップロード → 候補を確認・修正 → 採用したものだけ保存 |
| OGT に残るもの | 記録（文字・ハッシュ） | 記録＋利用者が選んだ抜粋 | 記録＋原本＋抜粋 | 記録＋原本＋抜粋＋AI の出力（候補） |
| 外部送信 | なし | なし | なし（セルフホストの保管先のみ） | **あり**（AI の提供元へ） |
| 負担の軽さ | 低 | 中 | 中 | 高 |
| 監査のしやすさ | 中（ハッシュで同一性は確かめられる） | 中〜高（抜粋と原本のハッシュが対応） | 高（原本を後から開ける） | 高。ただし AI の出力の扱いを決める必要あり |
| 新しく決める方針 | ほぼなし | 抜粋の保存範囲 | 保管・保存期間・削除・容量 | C に加え、AI キー・外部送信・提供元の保持方針・同意 |
| OGT 本体への影響 | なし | なし | **あり**（ストレージ・権限・削除・バックアップ） | **あり**（C＋秘密情報の保管・外部送信の経路） |

### 推奨

- **段階的に進める: A（済）→ B → 方針が決まったら C → D。**
- B は SSBJ 内で完結し、外部送信も保管先の新設もないので、方針の決定を待たずに正式な Issue にできる。
- C・D は、資料保管と外部送信の方針（§4）が決まるまで実装しない。D は C の保管・対応付けを前提にする（AI の出力を、元の資料の位置と結び付けて確かめるため）。

## 3. 根拠資料・抽出内容・要求項目・下書きの対応付け

### 3.1 データのつながり

```
根拠資料（原本）           抜粋                          要求項目            文章の下書き
ssbj_evidence  ─1:N─▶  抜粋（新設候補）  ─N:M─▶  要求 ID（マスター）  ─▶  文章の項目（ssbj_narratives）
 資料名・版・SHA-256       参照位置（頁・節）            REQ-GEN-001 など       下書き → 利用者が確認 → 開示する文章
 保管先（C 以降は原本）    抜き出した文                  ※ID は #49 で確定       内部メモに「どの抜粋から作ったか」
                           作成方法（手動 / AI）
                           確認した人・日時
```

- **抜粋**を新しい単位にする。根拠資料 1 件から複数の抜粋を作り、1 つの抜粋を複数の要求項目に対応付けられるようにする。
- **原本の単位のテーブルを別に持つかは未決（未決事項 14）。** 今の `ssbj_evidence` はレポートごと・項目 ID 必須の行なので、抜粋をそこにぶら下げると、
  「項目 ID」と「要求 ID」の二重の対応付けになり、同じ原本を複数のレポート・項目で使うときに原本の記録が重複する。
  原本（ファイル・SHA-256・保管先）を組織の単位で 1 行に持ち、`ssbj_evidence` と抜粋がそれを参照する形も比べる。
- 抜粋には「作成方法（手動 / AI）」「利用者が確認したか（確認した人・日時）」を持たせる。**確認していない抜粋は下書きにも根拠にも使わない。**
- 要求項目との対応は**要求 ID** で持つ（文章の項目 ID ではない）。一般基準と気候基準が同じ文章の項目に対応するため（`requirementMaster.ts` の冒頭の注記）。
- 抜粋は内部記録として扱い、開示側に出すのは今までどおり開示用参照文だけにする（`docs/ssbj-spec.md` §5 の列分け）。

### 3.2 下書きとの関係

- 下書きは、R2-03 の穴埋めテンプレートと同じく「利用者が選んだもの（ここでは確認済みの抜粋）を明示して作る」。根拠のない内容を自動で補わない。
- 下書きを開示する文章に入れるのは利用者の操作だけにする。AI の出力をそのまま開示する文章として保存しない。
- どの抜粋から作った下書きかを内部メモ（または別の内部列）に残し、後から根拠をたどれるようにする。
- 保存版に抜粋を含めるかは未決（§3.4・§3.5、未決事項 12・13）。含めると後から消せなくなるため（内部記録として含めれば、閲覧者には返さない。権限表 §2.3）。

### 3.3 削除・更新

- 原本を差し替えたら（SHA-256 が変わったら）、その原本からの抜粋は「要再確認」にし、下書き・開示する文章は自動で変えない。
- 根拠資料を削除するときは、抜粋と対応付けも一緒に削除する。保存版に残った内容は変えない（固定版の考え方と同じ）。
  ただし、個人情報を含む抜粋を保存版に固定すると、削除の求めや組織データの削除（R2-24、#91）で消せなくなる。§3.5 を参照。
- 作業中データの変更の操作履歴は、`ssbj_audit_logs` のトリガーで残る（新しいテーブルにもトリガーを付ける）。
  **外部 AI への送信は記録できない**: 送信はサーバの処理から行い、DB の行の変更を伴わないので、トリガーには残らない。送信の記録は §3.6 で別に決める。

### 3.4 見られる範囲（ロール）

| 対象 | 入力担当 | 承認担当 | 閲覧者 | 管理者 | 補足 |
|---|---|---|---|---|---|
| 抜粋（作業中） | ○ | 見るだけ | × | ○ | `ssbj-spec.md` §10 と権限表（`authorization-matrix.md`）§2.1 の作業中データと同じにする |
| 原本（C 以降） | 未決 | 未決 | × | 未決 | 未決事項 12 |
| 保存版の中の抜粋 | — | — | × | — | 閲覧者には保存版の内部記録を返さない（権限表 §2.3）。抜粋を保存版に入れるときは、内部記録に分類する（`utils/disclosedSnapshot.ts`） |

- 新しいテーブルは、`ssbj-spec.md` §10 と権限表 §2.1 に従う（組織分離・ロール別のポリシー・列 GRANT・承認ロック・操作履歴）。
- **原本の置き場の候補の `import-files` には、SSBJ のロールが効かない。** Storage のポリシーで組織の全員が読める（`20260831000003_storage.sql`）。
  本体の帳票（`activity-evidence/`）は、ブラウザからは消せず、消すのはサーバの処理だけにしてある（`20261026120000_activity_evidence.sql`）。SSBJ の原本も同じ形にできる。
  受け付ける形式は CSV・PDF・PNG・JPEG・WebP（帳票は PDF・PNG・JPEG・WebP）で、Office ファイル（Word・Excel・PowerPoint）は入らない。
  流用するなら、本体の帳票の仕組み（保存の流れ・行のテーブル・消し方）を広げる形で、形式とロールの扱いを本体側と決める（未決事項 2）。

### 3.5 個人情報

方針文書・議事録などの根拠資料には、氏名・役職・連絡先などの個人情報が含まれうる。今の案は「機微な経営情報」しか扱っていないので、次を決める（未決事項 11）。

- 資料・抜粋に含まれる個人情報を、そもそも取り込んでよいか。取り込む前に伏せ字にするか（利用者の手で / 自動で）。
- 外部 AI に送るとき（D）は、個人データの第三者提供に当たるか、提供元が国外なら外国にある第三者への提供（国外移転）に当たるかを確かめ、必要な同意・記録を決める。
- API キーは組織単位だけ（#3 の方針。個人の契約条件で会社のデータが送られる問題を避けるため）。使ってよい鍵は、法人契約で学習に使わない設定のものに限る。
- 個人情報を含む抜粋を保存版に固定すると、削除できなくなる。保存版には抜粋の本文を入れず、参照（どの原本の何頁か）と SHA-256 だけを入れる、などの両立のさせ方を R2-24（#91）と一緒に決める。

### 3.6 外部送信の記録（監査ログ）

外部 AI への送信（D）は DB のトリガーで記録できない。本体の共通の入口（`generateStructured`）が、送るたびに
`system_audit_logs` の `ai.request` に、誰が・いつ・どの用途で・どの提供元とモデルを・どの方式の鍵で・何を（種類・量・ファイルの SHA-256）送り・
結果がどうだったかを残す。鍵・送った内容・AI の出力は残さない（#3 の方針）。SSBJ もこの記録を使い、別の記録先を作らない。残るのは次の 2 点（未決事項 10）。

- `system_audit_logs` は組織の全員が読める（本体の RLS）。SSBJ が閲覧者に見せない内部記録として扱う資料の SHA-256 が、閲覧者にも読める形で残る。
  それでよいか（今も、保存版の CSV の出力の記録は同じ扱い。権限表 §2.3）。
- 「どの抜粋・下書きのために送ったか」を SSBJ の操作履歴（`ssbj_audit_logs`）にも残すか。

### Issue #3 の考え方を流用できるか

- **そのまま使う（#3 の方針で本体に実装済み）:** 共通の入口（`generateStructured`）・用途の登録（`src/lib/ai/purposes.ts`）・送る前の確認・鍵の管理（組織単位・管理者だけ）・3 社の提供元・回数の上限・監査ログ。AI を使う機能が守ることは [`architecture.md`](architecture.md) の「AI 連携」を正とする。
- **違う点:** #3 は請求書（数値）、R2-04 は方針文書（文章）。文章は量が多く、機微な経営情報を含みやすいので、送る範囲（未決事項 3）と出力の保存（未決事項 7）を #3 より厳しく決める必要がある。本体の入力は PDF・PNG・JPEG・WebP で 1 回 4MB までなので、Office ファイルは送れない（送るなら、文字を取り出す依存を足す提案が要る）。回数の上限（組織全体で 24 時間に 500 回）は、請求書の読取りと共有になる。
- **結論:** SSBJ だけの AI の仕組みは作らない。SSBJ 側で決めるのは「何を送り、何を残すか」（未決事項 3・7・8・10〜13）と、用途の登録の中身だけ。SSBJ の Route Handler で SSBJ のロール（入力担当か管理者）を確かめてから、共通の入口を呼ぶ。

## 5. SSBJ 内で完結する変更と OGT 本体に影響する変更

| 区分 | 変更 | 方式 |
|------|------|------|
| SSBJ 内で完結 | 抜粋のテーブル（組織分離・RLS・操作履歴のトリガー付き）と、要求 ID との対応付け | B・C・D |
| SSBJ 内で完結 | 根拠文書の画面に、ファイルを選んで箇所を抜き出す操作（ブラウザ内） | B |
